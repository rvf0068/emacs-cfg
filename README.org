Welcome! 🤓 This is my personal Emacs configuration, designed to be a comfortable and productive environment, especially for my work in *mathematics* and general programming.

This configuration is built using a *literate programming* approach. 📖 Almost all of the setup lives inside the =emacs-config.org= file. This means every setting and piece of code is documented in plain English, making it easy to understand and maintain. The =init.el= file is kept minimal—its only job is to load this Org file.

A primary goal here is to create a first-class environment for academic writing and *mathematics*. 🧑‍🏫 This config includes a robust setup for *AUCTeX*, which provides a powerful, seamless experience for writing LaTeX documents. It's tuned for easily handling complex formulas, managing citations, and previewing your work. But it is also configured for producing mathematical texts using *org-mode*.

Beyond LaTeX, the setup also includes *YASnippet* for powerful, time-saving code and text templates ⚡ (you can see custom ones in the =snippets/= directory). It also loads custom helper functions from the =lisp/= directory to add unique behaviors and streamline common tasks.

To use this, simply clone the repository into your =~/.emacs.d= directory. The next time you start Emacs, it will automatically bootstrap, install the required packages, and tangle the =emacs-config.org= file. Enjoy! 😊

* Private and machine-specific settings

The public configuration can start without =personal.org=. It creates
=local-data/notes/= and =local-data/library/= under the selected Emacs
configuration directory, with a separate Org Roam database for these default
notes. No bibliography is required for startup. This data directory is
ignored by Git.

For an existing notes collection or PDF library, copy
=personal.example.org= to =personal.org= and set your own paths.
Existing private settings remain valid; there is no need to replace them.
A single bibliography filename, a list of filenames, or nil is accepted by
both Org Cite and Citar. Relative paths are interpreted relative to the
Emacs configuration directory.

Explicitly configured directories are never created automatically. If the
notes directory is missing or inaccessible (for example, an unavailable
external mount), startup warns and skips Inbox creation and Org Roam
autosync, without substituting a different notes directory or clearing an
existing database. The Citar Org Roam integration is likewise not enabled
when the notes directory is unavailable. Mount or create the configured directory and restart
Emacs. Bibliography paths are not created or rewritten; files must exist
before you use them for citation searches.

* Package management

=early-init.el= disables automatic package.el activation before startup.
=init.el= bootstraps straight.el, registers Org and Transient before other
packages can load their built-in versions, and loads =use-package= explicitly.
External packages in =emacs-config.org= declare =:straight t= or their custom
recipe; built-in or already registered packages need no second installation.
Private settings in =personal.org= can still declare their own packages.

The lockfile =straight/versions/default.el= records the intended revisions.
For an existing installation, use =M-x straight-thaw-versions= when you
deliberately want to restore the recorded revisions, after checking for local
changes in package repositories. Use =M-x straight-freeze-versions= after an
intentional package upgrade to record the new revisions; review the lockfile
diff before committing. Normal configuration refactoring should not upgrade
packages. =org-fragtog= is no longer needed with Org's native LaTeX preview
mode; its lock entry has been removed. If you still have a private declaration
for it, remove that declaration before freezing again. This does not delete
any existing local package clone.

* Magit repository dashboard

=C-c m= still opens the current repository's status. Use =C-c M=
(=M-x magit-list-repositories=) to list repositories across selected roots.
Configure Magit's own option privately, for example:

#+begin_src emacs-lisp
(setq magit-repository-directories
      '(("~/Python/" . 1)
        ("~/.emacs.d/" . 0)))
#+end_src

Depth 0 lists the directory itself if it is a repository; depth 1
also discovers repositories directly inside a non-repository root.
Use deeper searches only when necessary. Discovery stops at a Git
repository and does not recursively enumerate its nested repositories.
Adapt the paths to each machine. Missing local directories are skipped
by Magit; no directories are created. The public configuration does not
set search roots or change the behavior of the ordinary status command.

To show branches, all three worktree change flags and upstream divergence
instead of the default version column, optionally set:

#+begin_src emacs-lisp
(setq magit-repolist-columns
      '(("Name" 28 magit-repolist-column-ident ())
        ("Branch" 20 magit-repolist-column-branch ())
        ("Flags" 5 magit-repolist-column-flags ())
        ("Behind" 6 magit-repolist-column-unpulled-from-upstream
         ((:right-align t) (:sort <)))
        ("Ahead" 6 magit-repolist-column-unpushed-to-upstream
         ((:right-align t) (:sort <)))
        ("Path" 60 magit-repolist-column-path ())))
#+end_src

The flags N, U and S indicate untracked, unstaged and staged changes.
Ahead/Behind compare with locally recorded upstream references, not
the current state of GitHub. In the dashboard use RET to open a
repository, g to refresh the display, m/u to mark/unmark, and f to
fetch marked repositories. Fetching updates remote-tracking references
and may require authentication; it does not merge changes into working
branches. If none is marked, Magit asks before fetching all listed
repositories. Nothing is fetched automatically.

* GPTel and GPTel-Magit

Configure the GPTel backend and authentication privately in =personal.org=.
The public configuration retains the existing GPTel-Magit model selection
and the curl-streaming compatibility fix for ChatGPT Plus OAuth. No package
pins or credentials are changed by this fix. GPTel-Magit expects one
complete response; the compatibility library collects streamed chunks,
handles the non-streaming fallback and discards incomplete responses
after errors or cancellation.

The normal GPTel command (=C-c g=) is unaffected. In Magit, the commit
generation and diff explanation commands send Git diffs to the selected
GPTel backend; review staged changes for credentials or confidential
material before invoking them. The regression suite tests the compatibility
callback protocol with synthetic responses, not a live authenticated request.
After updating, manually check a small non-sensitive staged diff with
the usual OAuth backend before relying on generated messages.

* Python project environments

For local Python and Org buffers, =uv-env.el= searches for the nearest
ancestor with a =pyproject.toml= and an executable =.venv/bin/python=,
stopping at the closest Git checkout boundary. This handles a shared
workspace environment above nested package manifests, while preferring a
usable environment in the package itself. It is a filesystem heuristic
for conventional uv layouts, not a full uv workspace membership parser.
Remote files and nonstandard environment locations are not auto-activated.

The Python shell interpreter, ordinary Babel Python command, executable
search path and subprocess environment are buffer-local. Refresh with
=M-x my/find-uv-venv=, inspect with =M-x rvf/describe-python-environment=,
or restore previous settings with =M-x rvf/uv-clear-environment=.
No environment or package is installed automatically. Explicit Jupyter
kernelspecs and already running Jupyter/Eglot sessions are not restarted
or silently redirected by this helper; choose the intended kernel and
restart an existing language server when changing environments.

** Eglot and project-local Python language servers

Both Python major modes activate the project environment before requesting
Eglot startup. If a project has a usable =.venv=, Eglot prefers its
=bin/pylsp=; a missing project server does not trigger automatic startup.
Outside an activated environment, Eglot uses =pylsp= on PATH.

For a uv project that you want to edit with Eglot, one option is to add
the server as a development dependency:

#+begin_src sh
cd ~/Python/pycliques-project
uv add --dev python-lsp-server
#+end_src

This is optional and changes that project's dependency configuration.
The Emacs configuration does not run uv or install a language server.
After installation, revisit a Python file or run =M-x my/find-uv-venv=
and then =M-x eglot=. Inspect resolution with
=M-x rvf/describe-python-environment=.

To opt out of automatic Eglot startup while keeping environment activation,
set in =personal.org=:

#+begin_src emacs-lisp
(setq my-python-eglot-auto-start nil)
#+end_src

If you deliberately want a PATH-based server when the project has no
=pylsp=, set =my-python-eglot-allow-global-server= to t instead.
A PATH-based server may analyze a different Python environment.

Eglot normally shares a server among Python buffers in the same project.
A nested package with a different environment does not automatically
get a separate Eglot session. To change the server executable or its
environment, run =M-x eglot-shutdown= in the managed project, refresh
the environment in the intended Python buffer, then run =M-x eglot=.
This is distinct from restarting or selecting Jupyter kernels.

** Using pycliques-project from Jupyter blocks

There are several ways to use the monorepo from Emacs. Choose whichever
fits your workflow; none of these alternatives is required as a global
default.

*** Launch Emacs in the project's uv environment

The original approach makes the project's Python and Jupyter executables
available to the entire Emacs process:

#+begin_src sh
cd ~/Python/pycliques-project
uv run emacs
#+end_src

Alternatively, launch from any directory without changing the shell's
working directory first:

#+begin_src sh
uv run --project ~/Python/pycliques-project emacs
#+end_src

These commands assume that Emacs is on PATH and that the project's
environment contains Jupyter. This approach is convenient when most
of your work in an Emacs session uses the same Python environment.
It also works for Org research notes stored outside the monorepo.

*** Register a dedicated Jupyter kernel

To launch Emacs normally and select the monorepo's interpreter from
individual Org documents, register a named kernel:

#+begin_src sh
cd ~/Python/pycliques-project
uv run python -m ipykernel install --user \
    --name pycliques \
    --display-name "Python (pycliques-project)"
#+end_src

Run this once per computer, assuming the virtual environment is kept
at the same path. Register it again if the environment is moved.
The kernel specification refers to the project's Python interpreter
(normally =~/Python/pycliques-project/.venv/bin/python=), not the
Python interpreter that was active when Emacs started.

Select it in a single Org block:

#+begin_example
,#+begin_src jupyter-python :kernel pycliques :session research
import pycliques
import pycombtop
import pyg6data
import pyhomrep
,#+end_src
#+end_example

Or choose it for a whole document:

#+begin_example
,#+PROPERTY: header-args:jupyter-python :kernel pycliques :session research
#+end_example

After editing the property, use =C-c C-c= on that line to refresh
Org's settings, or reopen the document. Individual blocks can then
omit the kernel header:

#+begin_example
,#+begin_src jupyter-python
import networkx as nx
import pycliques

G = nx.octahedral_graph()
G.number_of_nodes()
,#+end_src
#+end_example

The expected result is 6. This works even when the Org file is outside
the monorepo. To check the interpreter used by an actual kernel:

#+begin_example
,#+begin_src jupyter-python :kernel pycliques :session research
import sys
sys.executable
,#+end_src
#+end_example

Use different session names for independent computations, and start
a new session if you need to change the interpreter of an existing
session.

*** Make Jupyter available when Emacs starts normally

Ordinary Python and LaTeX Babel blocks do not require Jupyter.
The public configuration enables emacs-jupyter when its configured
executable is available at startup.

If the Jupyter CLI is already discoverable, you need not change anything.
Check =(executable-find "jupyter")= with =M-:=.
Otherwise, set its executable explicitly in =personal.org=, for example:

#+begin_src emacs-lisp
(setq my-jupyter-executable
      "~/Python/pycliques-project/.venv/bin/jupyter")
#+end_src

This uses the CLI directly without adding the monorepo to the global
PATH or changing ordinary Python resolution. Restart Emacs. The command
=M-x rvf/describe-python-environment= reports the configured Jupyter
command and whether it is available. The Jupyter CLI and the kernel's
Python interpreter need not be in the same environment.

If the optional setting is nil, the existing upstream
=jupyter-executable= setting (normally ="jupyter"=) is honored.
An absolute CLI path is intended for local Jupyter; remote usage may
require a host-specific executable configuration.

*** Optional default kernel

If most Jupyter Python blocks use the monorepo, register the named kernel
as above and set this in =personal.org=:

#+begin_src emacs-lisp
(setq my-jupyter-python-kernel "pycliques")
#+end_src

Restart Emacs. Explicit kernel headers in documents and blocks take
precedence, and already running sessions are not redirected. This is
optional: if you often use several environments, leave the setting nil
and choose kernels explicitly. Existing customizations of Jupyter header
arguments are retained when the new setting is omitted.

*** Comparison

| Method                              | Special launch | Scope                              |
|-------------------------------------+----------------+------------------------------------|
| =cd ...; uv run emacs=              | Yes            | Whole Emacs process                |
| =uv run --project ... emacs=        | Yes            | Whole Emacs process, any directory |
| Named kernelspec                    | No             | Individual Jupyter blocks/files    |
| Named kernelspec as default         | No             | Default Jupyter Python blocks      |
| Automatic =uv-env.el= discovery     | No             | Local project buffers              |

The automatic project environment helper is complementary: it selects
ordinary Python and subprocess executables for local project buffers,
but it does not replace an explicitly selected Jupyter kernel or
redirect an already running session. For Org files outside a workspace,
a named kernel or the original uv launch approach is still needed to
use the monorepo. Try both approaches before choosing a personal default.

* Regression tests

The test suite uses a temporary home directory, copies the public configuration
and installs packages using the recorded straight versions. It does not read
personal.org or custom.el from your real Emacs directory.

#+begin_src sh
make test
#+end_src

Use =make test-unit= for the original ERT suite, =make test-workflows= for
both real workflows, or =make test-latex= and =make test-jupyter= separately.
Set =EMACS=/path/to/emacs= on the make command line to test another executable.
Run =make doctor= to check executables, TeX files and Python dependencies before
downloading packages. =make doctor-unit= checks only unit-suite prerequisites.
All graphical targets initialize the full public configuration and currently
require the same Python and TeX dependencies. The full suite and
=make test-workflows= run the real graphical workflows both with temporary
private settings and without =personal.org=. They also test startup with
an unavailable explicitly configured notes directory and check that the
original Org Roam database is unchanged. The unavailable-directory scenario
also disables Jupyter and checks that ordinary Python and native LaTeX
previews still work. The regular graphical runs exercise a dedicated
kernel in a separate virtual environment with a test-only module, as well
as the original registered kernel. The test environment reuses installed
Python dependencies through a test-only .pth file, without downloading
another copy of them.
The graphical tests require graphical Emacs with SVG and dynamic module support,
xvfb-run, xauth, GNU timeout, TeX Live (including lxfonts, AMS packages and
mylatexformat), dvisvgm, and Python with Jupyter, IPykernel, NumPy, NetworkX
and Matplotlib on PATH. PDF Tools and ZeroMQ need their native dependencies.
Set =RVF_EPDFINFO= to the path of a working epdfinfo if it is not on PATH.
The unit suite also requires ripgrep (=rg=) to verify the Org notes search
against real files. The suite downloads and builds packages in a temporary directory. The unit
runner registers its selected dependencies using the literal straight recipes
in =emacs-config.org=, without evaluating the configuration or eagerly loading
the packages.

** Local settings with uv

For an Emacs executable outside PATH and a Python environment managed by uv,
copy =Makefile.local.example= to =Makefile.local= (ignored by Git) and set:

#+begin_src makefile
EMACS = /opt/emacs-32-noble/bin/emacs
UV_PROJECT = $(HOME)/Python/pycliques-project
#+end_src

Then run =make doctor= and =make test= from this repository. The Makefile uses
=uv run --project= when =UV_PROJECT= is set; normal uv environment synchronization
rules apply. Make sure the selected project's environment includes the Python
dependencies listed above. No real Emacs personal settings or package caches are
used by the tests. Without local settings, the original PATH-based commands work
as before. Command-line assignments override the local file.

The equivalent one-off command, without creating a local file, is:

#+begin_src sh
cd ~/Python/pycliques-project
uv run make -C ~/emacsen/math-emacs test \
    EMACS=/opt/emacs-32-noble/bin/emacs
#+end_src

Use [[file:samples/workflow-test.org][the interactive test document]] for manual preview editing and
PDF export checks on your usual Emacs version. Automated tests now cover
native LaTeX preview regeneration after editing and a Beamer setupfile;
interactive completion, live side-by-side previews and PDF export still need
manual checks.

** CI dependency image

GitHub Actions runs the full suite on pull requests, pushes to =main= and
manual dispatches. The job uses the Ubuntu 24.04 image defined in
=.github/ci/Dockerfile=, with graphical Emacs, the previously validated TeX
dependency closure, native module dependencies and a Python kernel environment.
The image is built only on a cache miss and stored as a compressed Docker
image archive in GitHub Actions cache. The exact cache key includes the
Dockerfile hash, runner OS/architecture and UTC calendar month so changes
and periodic refreshes rebuild dependencies. A first run after merging or
cache eviction may take longer; PR caches cannot populate the main branch
cache. No container registry, external credentials or package publication
are required. GitHub may evict caches; no cache is required for correctness.

The regression still runs =make doctor=, the missing-executable diagnostic,
and every test in =make test=. The container mounts the checkout read-only
and runs as a non-root user. Its test home is created afresh by the existing
runner; neither the configuration, personal settings, nor Emacs package
builds are included in the cached image.

On a machine with Docker, the equivalent full test run from a clean checkout
is:

#+begin_src sh
docker build --pull -t emacs-regression:ci .github/ci
docker run --rm --init \
    --mount "type=bind,source=$PWD,target=/workspace,readonly" \
    emacs-regression:ci make test EMACS=emacs UV_PROJECT=
#+end_src

The Docker route is optional for local testing. Ordinary Makefile targets
and the uv-based setup above remain unchanged. To force a fresh image in
CI, delete the corresponding cache in the repository's Actions cache
settings, or edit the Dockerfile. Compare cache-hit runs with the earlier
native-installation runs before judging performance.
